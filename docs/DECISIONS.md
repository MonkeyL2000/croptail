## <a id="plant-cells"></a>Basic_Plants.png 的格子含义是「按像素分析定的」,不是猜的

**背景**:素材包没有配图集说明,`Basic_Plants.png`(96x32,6x2 格)到底是什么作物、
哪一列是哪个生长阶段,只能自己看。

**怎么定的**:用 Python + Pillow 把每格 16x16 的主色/不透明度粗采样了一遍,再用
「按调色板量化成字符画」的方式把它打印成文本图,肉眼读出来的:

| 列 | 行 0(由绿转黄) | 行 1(常绿叶菜) |
|---|---|---|
| c0 | 土堆(只有土色,透明外框) | 小土堆 |
| c1 | 幼苗,矮 | 小苗,矮 |
| c2 | 中等 | 中等 |
| c3 | 高,已偏黄 | 高 |
| c4 | 高,最黄(成熟) | 高,顶端有穗 |
| c5 | 石头(不是作物,与 r0 相同) | 石头 |

**决策**:`wheat` = 行 0 的 c1..c4,`greens` = 行 1 的 c1..c4,各 4 个生长阶段。
**理由**:两行的色相差异(黄化 vs 常绿)正好对应两种作物,4 个尺寸就是 4 个阶段。
**风险**:这是**像素级推断**,不是官方说明。若日后发现错位,只需改
`scripts/farm/crop_db.gd` 里的 `stage_cells` 坐标,逻辑层不用动。

## <a id="cell-sprites"></a>农田逐格用 Sprite2D,不用 TileMapLayer

**决策**:每一格农田是一个 `FarmCell`(Node2D + 2 个 Sprite2D),由 `FarmPlot` 用代码生成。

**理由**:素材里**没有**湿土贴图,湿/干必须靠逐格 `self_modulate` 区分;
`TileMapLayer` 的 modulate 是整层级的,做不到逐格染色。逐格节点还让「土壤 + 作物」
两层叠加、成熟高亮都变成一行属性赋值。

**被否决**:TileMapLayer 画土 + 另一层画作物 —— 湿土染色无解,得自己复制一套调色后的贴图。

**代价**:格子多时节点数 = 列 x 行 x 2(现在是 84x2)。当前规模无所谓;
真要上千格再考虑换 `MultiMeshInstance2D` 或烘焙贴图。

**⚠️ 踩过的坑:格子里的 Sprite2D 必须自己摆到格子中心。**
格子的原点是**左上角**,而 `Sprite2D` 默认 `centered = true` ——
`Sprite2D.new()` 之后不设 `position`,那块 16x16 的贴图就会**以左上角为圆心**画,
整块偏左上 8px。后果:土块/作物画在错误的位置,玩家看到的正是
「指示器的格子和实际作用的格子不是一个格子」(用户第二次报的就是这个;
逻辑层全绿 —— `region` 是对的,只有看画面才发现)。

修法:`FarmCell.SPRITE_OFFSET = Vector2(CELL_SIZE * 0.5, CELL_SIZE * 0.5)`,
土块和作物精灵都用它。`farm_props.gd` 里是 `centered = false` + 自己算底边中心,同理。

**两条回归**(自检 163 项里):
1. `the soil sprite covers exactly its own cell` —— 拿精灵自己的 `global_transform`
   算可见矩形,必须**逐像素等于**格子的矩形。顺手记一笔:这个 helper 第一版是手算
   `cell.to_global(get_rect().position)`,漏了 `sprite.position`,反过来冤枉了正确的代码。
2. `tilling repaints nothing outside that cell` —— 端到端拿画面量:把相机对准一格、
   藏起角色,锄它,然后逐像素比较前后两帧(64x64 区域,含先量一次「什么都不做」的对照),
   变化的像素必须**全部**落在那格的 16x16 里。实测 `256/256 inside, 256 in the area`。
   把偏移改回 `(0,0)` 复现 bug 时它是 `64/256 inside, 256 in the area` —— 正好是
   「四分之三的土块落到了左上方那格」,和用户描述一致。

**顺带**:截图工具现在默认把整块农田锄一遍(`till_plot`),土块是纯色平板,
于是整块农田 = 一个 192x112 的色块,边界必须正好压在农田外框上 ——
实测包围盒 `x 304..495, y 66..177` = 期望值,四边外一圈全是草像素。

## <a id="auto-walls"></a>水的碰撞墙在运行时按**岛的轮廓**自动生成

**决策**:`scripts/world/farm_map.gd` 在 `_ready()` 里看**草地层**的每一格,凡四个
邻居里哪个不是草,就在**那个邻居格**上记一笔墙 —— 墙铺在草地外面,玩家才能一直走
到岸边;同一行的墙按行合并成长条。实测 76 个碰撞形状。

**理由**:原项目 TileSet 完全没有物理层(栅栏、房子、水都不是障碍),但农场游戏又必须
「走不出岛」。手刷物理层是不可见的重复劳动;按层数据生成是确定性的、跟地图编辑同步、
零手工维护。

**改过一次,因为坐标系**:第一版是「水格减去草格」。但 `water` 层挂在 (0,0)、
`grass` 层挂在 (-8,-5),两层的格坐标**差半格** —— 整数格坐标相减得到的墙会整体
横移一格。后果很难看也很隐蔽:

- 左边多出一堵玩家看得见草地却过不去的**隐形墙**(玩家走不到岸边)
- 右边漏出一条能**走到水面上**的缝

真正的原因是「拿水层的网格去描述岛的形状」这件事本身就不对:墙的位置就是岛的边,
那就该用**草格**算。现在完全不读水层,墙和水岸分毫不差。

**这条 bug 差点漏掉**:当时的断言只写了「玩家没走进水里」,而隐形墙**正好能让这条
通过**。现在断言写成量的:草左沿 x=-264,玩家(脚下碰撞圆半径 5)必须停在 -259 ± 1px。

**被否决**:
- 给 TileSet 手刷 physics layer —— 每次改地图都要重刷,容易漏。
- 用 `Terrain` 的 peering bits 做水岸碰撞 —— 那套是给地形自动拼接用的,和碰撞无关。
- **把墙铺在草格自己身上** —— 那样玩家连最外圈那一格草都上不去,岸边就不能站人了。
  铺在外面的邻居格上,玩家才能贴着岸走。

**注**:合并成长条而不是逐格一个碰撞体,是因为逐格碰撞在角色移动时数理化代价明显,
而这一层不会有半格高度的形态。墙往外铺 4 格(`WALL_THICKNESS`),这样就算以后有东西
把玩家丢到岛外,他也不至于在水面上乱跑。

**验证**:自检里有一条真走一遍 —— 挑一行「从岛的最左一格开始连着几格都空」的草地,
把玩家放上去往左走 1.5 秒,量他最后停在哪。

## <a id="grass-terrain"></a>草地/泥地的图块不能自己指派,要让引擎按 peering 算

**决策**:地形的 `atlas` 坐标一律由 `TileSet` 的 terrain 数据算出来
(`terrain_set_0` mode 0 = Match Corners and Sides,terrain 0 = grass),
工具是 `scripts/dev/retile.gd`(调引擎的 `set_cells_terrain_connect()`)。

**理由**:这是「草坪全是错的」那个 bug。地图形状是脚本刷的,刷的时候**每一格都写了
同一个 atlas 坐标** —— 而那一格是**左上角块**。结果整片草坪被角块铺满,边缘反倒没有
边块。这不是随便挑错了块,而是「哪一格画哪一块」本来就不是常量:

| 位置 | 该用哪块 | 八向里几个邻居是草 |
| --- | --- | --- |
| 内部 | `(1,1)` | 8/8 |
| 上边 | `(1,0)` | 5/8(上排三格不是)|
| 下边 | `(1,2)` | 5/8 |
| 左边 | `(0,1)` | 5/8 |
| 右边 | `(2,1)` | 5/8 |
| 四个角 | `(0,0) (2,0) (2,2) (0,2)` | 3/8 |
| 内凹角 | `(5,1) (5,2) (6,1) (6,2)` | 7/8(只差一个斜角)|

**peering 表的读法**(`docs/art/terrain_grass.png` 把它画成了九宫格):
`.tres` 里 `x:y/0/terrains_peering_bit/<方向> = 0` 表示「这个方向上也是草」。
**没列出来的方向 = 那个方向不是草**,不是「无所谓」。拿八向掩码去对,才能唯一确定一块。

**为什么让引擎算而不是自己写**:这张表有 32 块(8x4),手抄 8 位掩码笨且必错,
而且错了不报错 —— 只是画面不对。引擎自己就是标准答案。

**怎么确认方法是对的**:把**旧地图(263 格)当标准答案**跑一遍。那是原作者在编辑器里
用地形笔刷点出来的,坐标一定是按 peering 算的(它的 13 种块刚好组成一张像样的草地边缘)。
重算结果和存着的**逐格一致(0 处不同)** → 方法可信,再去改那张 1938 格的新地图。
那个快照就留在 `scenes/dev/grass_terrain_ref.tscn`,工具每次跑都会先校验它。

**验证**:自检里有一条拿**同一个 TileSet** 开一块临时 TileMapLayer,把同样的格子集合
再交给引擎算一遍,逐格对比 —— 不自己实现 peering,就不会因为「我的规则和引擎不一样」
而给出一个自洽但错的答案。另外断言内部那块必须是 `(1,1)`。

**注意**:改地图形状(刷格子、加岛、挖洞)之后**必须重跑 `retile.gd`** ——
新加的格子默认还是那个角块。这也是为什么 `retile.gd` 和参考图快照都进了仓库:
它不是一次性脚本,而是「改了地图就要跑一遍」的流程工具。

## <a id="no-daynight"></a>只推进「天」,不做昼夜光照

**决策**:`TimeManager` 只管日期与进度(45 秒一天,按 T 立刻过一天),不做画面变暗/灯。

**理由**:昼夜光照需要 CanvasModulate 曲线、灯光层、以及「晚上还干活吗」的一堆规则,
而当前要验证的是种植循环本身。日期已经是循环的驱动(浇水→过天→生长),光照纯装饰。

**被否决**:先做昼夜再补种植 —— 装饰先于玩法,容易把时间预算烧在调色上。

## <a id="ascii-ui"></a>所有 UI 文案用 ASCII

**决策**:HUD、提示、控制台输出一律英文 ASCII。

**理由**:Godot 内置默认字体不含 CJK 字形,中文会渲染成豆腐块,除非额外塞一个中文字体
(几百 KB 且要配主题)。这个项目本来就非商业个人玩,英文文案零成本。

**被否决**:引入中文字体 —— 现在不值得;真要本地化再说(那也是一次性替换主题字体)。

## <a id="deferred-on-enter"></a>状态机的 `on_enter()` 必须延迟调用

**决策**:`NodeFiniteStateMachine._ready()` 里用 `current_state.on_enter.call_deferred()`。

**理由**:`_ready()` 是自下而上执行的 —— 状态机子节点先于父节点 `Player` 就绪,
所以进入初始状态时 `Player` 的 `@onready var animated_sprite` 还是 `null`,
`on_enter()` 里 `play_anim()` 直接崩(`Invalid access to property 'animation' on Nil`)。
延迟到本帧末,父节点的 ready 已经完成。

**被否决**:在每个状态的 `on_enter()` 里自己判断 `if sprite == null` —— 把坑分散到所有状态里。

## <a id="signal-param"></a>`NodeState.transition` 信号必须带参数

**决策**:`signal transition(state_name: String)`,配套 `@warning_ignore("unused_signal")`。

**理由**:原代码是 `signal transition`(无参)却到处 `transition.emit("walk")`。
Godot 4 只在**真的发出信号时**才检查参数个数,所以平时不报错,
一按方向键就 `Error calling from signal ... too many arguments`,直接卡死。
自检里的 `transition signal carries the state name` 就是这条的回归测试。

**被否决**:保留无参信号、改用「自己找目标状态」的写法 —— 状态之间会耦合成网状。

## <a id="autoload-not-static"></a>`GameState` / `TimeManager` 的方法不写成 static

**决策**:autoload 脚本里的公开函数都是普通实例方法,靠 autoload 单例名调用。

**理由**:`seed_item_id()` 一开始写成 `static func`,F5 一跑引擎就报
`The function "seed_item_id()" is a static function but was called from an instance`。
在验证脚本里 `static` 是必需的(代码不在场景树里),但这里 autoload 已经提供了单例,
再叠 `static` 只会两边都别扭。

## <a id="class-name-cache"></a>新增 `class_name` 脚本后必须让编辑器重扫一次

**决策/流程**:每次**新增**带 `class_name` 的脚本后,用 MCP `launch_editor` 打开一次项目
(等 15~20 秒让编辑器建 `.godot/global_script_class_cache.cfg`),再关掉、再 `run_project`。

**理由**:`run_project`(godot -d)启动时**不会**重建全局类名缓存。新加的 `class_name`
在缓存里查不到,就变成 `Parser Error: Identifier "CropDB" not declared in the current scope`,
而且报错位置指向**使用方**(`game_state.gd`)而不是新文件,很容易被带偏。

**被否决**:手写 `.godot/global_script_class_cache.cfg` —— 那是缓存,格式随版本变,
而且 `run_project` 也不接受 `--import`。

## <a id="action-blocks"></a>`Basic Charakter Actions.png`:2 列 = 两帧,12 行 = 3 个动作 x 4 个朝向

**决策**:一个 `use_*` 动画 = 图集的**一行**(2 帧),行号 = `组起始行 + 朝向序号`。
`TOOL_ACTION` 给每组工具的**起始行**,`DIR_ROW = {front:0, back:1, left:2, right:3}`
给组内偏移。表在 `tools/gen_player_scene.py`。

**理由(踩过两次)**:

这张图是 **96x576 = 2 列 x 12 行**,每格 48x48。2 列 = 一个动作的两帧;
12 行 = **3 个动作 x 4 个朝向**,每 4 行一组,组内顺序和立绘表一样(前 / 后 / 左 / 右)。

1. 第一次错:按「每行一个动作、x 取 0/48/96/144」切 —— 96 宽的图上 x=96/144
   已经出界,每个动画的第 3、4 帧是空的。不报错,只是动作永远播不全。
2. 第二次错(用户报的「锄地、收割、浇水…会朝两边施放动作」):把 `2b, 2b+1`
   两行当成「一个动作的 4 帧」,于是一个动画里左一帧、右一帧交替;
   更糟的是 `use_*_left` 和 `use_*_right` 拿到**同一对行 = 同一个动画**,
   所以左右两边看起来一模一样。

**怎么定版式(可复现,不靠「看起来像」)**:

- 块内行两两比:正常差异 vs 对方镜像 —— `d(行2帧0, mirror(行3帧0)) = 0 像素`,
  即这两行是**互为镜像的一对**(两个朝向),不是同一朝向的两帧。
  行 2/3、6/7、10/11 都是精确镜像(重叠像素 0 个,`ImageOps.mirror` 实测)。
- 行 0/1/4/5/8/9 的头左右对称、居中、带两个耳朵状凸起 => 前/后视图;
  行 2/3/6/7/10/11 的头偏一侧且窄 => 左/右视图。
- 前/后靠**脸上的肤色像素**分:立绘表 `front` 头部有 `(232,181,172)` 8 颗、
  `back` 0 颗。实测行 0/4/8 有 5~8 颗 => front,行 1/5/9 是 0 颗 => back。
- 左/右两行本身是精确镜像,立绘表也是 —— 所以**左右谁排在前是画师的约定**,
  无法从像素区分;跟立绘表取同一约定(前/后/左/右)。若哪天发现左右反了,
  交换 `DIR_ROW` 里的 left/right 即可。

**哪个动作是哪个工具**(数手里那件东西的像素):

| 组 | 行 | 证据 | 工具动作用途 |
|---|---|---|---|
| A | 0-3 | 金属 92px / 木 56px,长柄 + 箍,从**头顶**抡到地面 | 锄头 |
| B | 4-7 | 金属 134px / 木 55px,从**体侧**扫到地面 | 镰刀 => 收割;播种借它 |
| C | 8-11 | 纯金属 432px / **木 0px**,大件,在身前低位倾倒 | 洒水壶 |

**验证**(自检里三条,都是这次新加的真回归):

- `each use animation has 2 frames (one atlas row = one direction)`
- `each direction of a tool uses its own atlas row` —— 一个动画只能来自一行,
  且四个朝向必须落在**四行不同**的行上。旧错法直接挂在这里。
- `left frames are the exact mirror of the right frames` —— 逐帧比像素,证明
  动画里没混朝向。此时**不能直接比 `get_data()`**:导入器开着
  `process/fix_alpha_border`,它会把全透明像素的 RGB 抹成邻居颜色(免得缩放出黑边),
  而那个抹痕对镜像不对称 —— 实测 6 对帧真实差异 0 像素,却报了 3 个 FAIL。
  改成只比 alpha 蒙版 + **不透明**像素的颜色。
- `front action frames show the face, back frames do not` —— 拿上面那条肤色证据
  反向验证前/后没接反。

## <a id="tools-sheet"></a>`Tools.png` 不是「6 种工具」,是「3 种工具 x 6 个朝向」

**决策**:一个游戏工具占**一整组**(两行),不是某一格。表在 `scripts/ui/tool_icons.gd`。

**理由**:这是「工具的素材好像全都用的同一种」那个 bug 的根。96x96 有 36 个非空格子,
旧表从行 2/3 里挑了 3 格 —— 那是**同一把工具的 3 个朝向**,于是 4 个工具里 3 个长得一样。

逐行数像素(金属灰 vs 木色)分三组:

| 行 | 金属 px | 木 px | 手里那件东西 |
|---|---|---|---|
| 0 / 1 | 308 / 289 | 0 / 0 | 纯金属大件、带壶嘴 => **洒水壶** |
| 2 / 3 | 110 / 110 | 72 / 44 | 金属头 + 长木柄 => **锄头** |
| 4 / 5 | 54 / 54 | 72 / 46 | 木件 + 一条金属箍 => 第三件工具 |

**第 4 个工具(收获)直接取成熟作物的贴图**(`Basic_Plants.png` 第 4 列),
语义上正好是「你要收的东西」,而且一定和前三张不像;它还会跟着当前选中的作物变。

⚠️ **存疑待确认**:第 4 行那件东西按像素看是「木件 + 金属箍」,**不像种子袋**。
种子图标现在就取它(`Tools(0,4)`)—— 「四个图标互不相同」这条需求满足,
但「它到底是不是种子袋」没验。见 `docs/PROGRESS.md` 的待确认项。

**验证**:自检逐像素比较四张图标贴图,不是比重了算(`_distinct_icon_count`)——

最后还拿截图做了模板匹配,四个格子都是**逐像素 0 误差**命中各自的目标格。

## <a id="bitmap-font-yoffset"></a>BMFont 的 `yoffset`:Godot 不按文档来

**决策**:`tools/gen_pixel_font.py` 里存的是「字形顶到 ascender 顶的距离」,
即 BMFont 文档语义的 `yoffset + base`。

**理由**:实测(Godot 4.3)的规则是

    字形顶 = Label 顶端 + yoffset        (base 不参与绘制)

而 BMFont 文档说 `字形顶 = 基线 + yoffset`、`基线 = 顶端 + base`。按文档写,
整行字会**上移一个 base**:12px 字体就上移 12px,顶栏里只剩字的下半截、顶被裁掉。

**最坑的地方**:`get_ascent()` / `get_height()` 这些度量**全都是对的**,
从度量接口根本查不出来 —— 只能真的去量像素。
所以自检里有一个 `_measure_font_baseline()`:开一个探针 Label(黑底 + 已知坐标),
读一帧画面,量 'D' 的墨迹落在第几行,断言它正好是 `ascent - 大写高` 到 `ascent - 1`。

**证据**:探针 Label 放在 y=204、`yoffset=-9` 的 'D' 实际画在 y=195..203。

**教训**:遇到「文字/图形位置不对」,先造一个**背景干净、坐标已知**的探针去量,
不要在真实画面里靠数格子猜 —— 后者掺着相机变换、面板底色、窗口缩放,
量出来的东西不一定是你在找的那个。

## <a id="hud-theme"></a>HUD 的字体和字号必须在代码里显式设置

**决策**:`hud.gd::_apply_theme()` 建一个 `Theme`,**同时**设
`default_font` / `default_font_size` 和 `set_font("Label", ...)` / `set_font_size("Label", ...)`,
再挂到四个面板上。

**理由**:两个独立的静默坑。

1. **只设 `Theme.default_font` 不够**。实测 `Label.get_theme_font("font")` 会回退到
   Godot 内置的 Open Sans,位图字体根本没被用上 —— 不报错、不警告,
   只是字「看起来还行但不太对」。
2. **字号不钉死会放大点阵字**。位图字体只有一个真实尺寸(12px),
   而 `Label` 从默认主题拿到的是 16,Godot 于是按 16/12 缩放,
   行高从 15 变 20,字顶被顶出面板裁掉。

**被否决**:写在 `hud.tscn` 的 `Theme` 子资源里 —— 那样第 1 条就复现了,
而且在 .tscn 里没法断言。放代码里才能让自检真的查到。

**验证**:`_check_hud_layout()` 断言字体名是 `SproutUI-12`、字号是 12、行高是 15,
并且**读一帧真实画面**确认 DayLabel 的墨迹行完整落在自己的矩形里。

## <a id="reimport"></a>换了 `game_source/` 里的资源,必须 `launch_editor` 一次

**决策/流程**:改 `.png`/`.fnt` 等**被导入**的资源后,`launch_editor` 开一次项目、
等它重新导完、再关掉,然后才 `run_project`。新增 `class_name` 脚本同理。

**理由**:`run_project`(即 `godot -d`)**不会**重新导入资源。它拿的是
`.godot/imported/` 里的旧缓存,并且**一声不吭** —— 于是你会一直在量/看旧的东西,
还以为自己的改动没效果,顺着错误的方向查很久(这次就是:改了三版字形度量都没生效)。

**自查**:比对 `.godot/imported/<hash>.md5` 和源文件的 mtime,前者应该更新。

**教训**:「改了没反应」先怀疑**没重新导入**,再怀疑代码。

## <a id="frame-mixing"></a>测试里别拿一个层的**格坐标**去查另一个节点的格子集合

**决策**:凡是涉及「格」的比较,先把世界坐标算出来,再用**目标节点自己的**
换算函数转过去。`FarmProps.to_local_cell(global_point)` / `cell_center(cell)` 就是入口。

**理由**:`scenes/world/farm_map.tscn` 里各层有各自的 `position`:

**测试没转**。

**教训**:坐标系不统一的时候,「看起来对的数字」最危险 —— -216 和 -259

## <a id="synthetic-input"></a>合成按键(`Input.action_press`)不可靠,测试别依赖它

**决策**:自检里,凡是验**物理/碰撞**的用例,直接给 `velocity` 然后自己调

**等条件(等到真的动了)并设上限**,不要写死等 N 帧。

**理由**:同一个测试连跑 4 次,结果分别是「玩家走到 -248.9」「走到 -232.9」

**验证**:`player moved towards the shore` 现在连续 4 次都是
`岸边: 草左沿 x=-264.0, 玩家停在 x=-259.0, 期望 -259.0`,零抖动。

## <a id="targeting"></a>目标格 = **脚下**那格 + 朝向一格,不许用 `global_position + facing * 16`

**决策**:`Player.target_cell()` 写成
`standing_cell() + facing_cell_offset()`,其中
`standing_cell() = farm_plot.world_to_cell(cell_anchor_position())`,
`cell_anchor_position() = global_position + $CollisionShape2D.position`(即脚下那个圆的圆心)。

**理由**:用户反馈「锄地不知道会把哪块地处理掉,而且有点歪,不是正前方那块」。
两个原因叠在一起:

1. `global_position` 是**身体中心**,而脚下的碰撞圆在 `(0,6)` —— 差 6px。
   老写法 `world_to_cell(global_position + facing * 16)` 拿身体中心当锚点,
   上下朝向会**差一整格**;而且在格子里左右挪几像素目标格会跳。
2. 目标格必须是「脚下那格 + 1」,和站位在格内的偏移无关。

改完之后:站在格内任意位置结果一致;站在农田外面朝上能锄到贴边那排。

**验证**(自检 `-- tool targeting`,9 条):
四个朝向都是「脚下格 + 一格」;格内 ±5px 抖动目标不变;
**回归用例**:身体中心压在格子边界上方 2px(脚下已在下一格)、面朝下,
目标必须是 `(4,5)` —— 老写法在这里给的是 `(4,4)`,正好是玩家自己站的那格;
站在农田下沿外面朝上够得到最下一排。

**教训**:凡是「玩家在连续空间、格子是离散空间」的映射,锚点写错一格不是崩,
是**差一点点**——这种最容易被当成"手感问题"而不是 bug。

## <a id="target-indicator"></a>面前那格的指示框画在**最上层**(包括角色之上)

**决策**:`scripts/farm/target_indicator.gd`(`Node2D` + `_draw()`),节点摆在
`main.tscn` 里 FarmMap / Player **之后**,即盖在所有东西上面;
农田内 = 奶油色框线 + 16% 白填充,农田外 = 暗灰框线、不填充。

**理由**:

1. 玩家自由走位、没有格对齐,光看站位判断不出目标格 —— 需要把「工具会作用到
   哪一格」直接画出来。
2. 它和 `use_current_tool()` 调的是**同一个** `Player.target_cell()`,
   所以框画在哪、工具就一定作用在哪(自检先读框、再真锄一次比对)。
3. **不能**画在地面层(角色之下):角色精灵是 48x48、比一格(16px)大得多 ——
   从真实截图量出来,面朝上时面前那格整格都被角色盖住,一条框线都看不见。
4. **不能**用 `z_index = -1`:负 z 会被父节点的 z 抵消下场(`z_as_relative`),
   连农田底板都盖不住 —— 这个坑在写的时候躲过一次。
5. 线宽 1 是**压在矩形边上**画的,所以往里收 `LINE_INSET = 0.5` 才正好落在
   格子的最外圈像素上(收 1px 会少一格像素、看着往左上偏)。

**验证**(自检 6 条 + 真实截图):
* 「框的格子 == 真正被锄的那格」「框跟着朝向走」「必须画在 FarmMap 和 Player 之后」;
* 墨迹检查:同一格采样 25 点(含边框线),框开着 luma 0.821 / 藏起来 0.786 ——
  证明它真的产生了像素(量的时候先把角色藏起来,否则量到的是角色的腿);
* 截图逐像素:农田内 `(0,1)`/`(4,6)` 都是**完整 16x16 方框**(奶油线 + 白填充),
  农田外 `(15,15)` 只有暗灰框线、无填充。

* 免费包**没有**斧/镐,也**没有**「砍」的动作 —— chopping/fishing 都是付费包内容。
  有人在该页面问过镐头/钓鱼,作者的回答就是「在那两个包里」。

免得以后有人以为是漏改。

**规则集中在两处**,别的代码不许自己判断:
* `GameState.tool_works_on_props(tool_id)` —— 哪些工具是「对地面物件动手」的(只有斧、镐);
* `FarmProps.can_use()` / `use_tool()` —— 谁能敲什么、敲完给什么。

## <a id="ponds"></a>池塘 = **删掉草地格**,不是画水

**决策**:`tools/carve_ponds.py` 把 3 个椭圆(带 sin 抖动的边)范围内的**草地格删掉**,

**必须配套**:改完地图**形状**要跑 `res://scenes/dev/retile.tscn` 再

## <a id="landmarks"></a>围栏 / 鸡舍 / 鸡是**手摆**的,不进随机撒点

**决策**:`farm_props.gd::_place_landmarks()` 在撒道具**之前**手摆:
* 围栏圈 `PEN_RECT = Rect2i(33, 3, 7, 6)`(草地层格坐标),
* 鸡舍 `HOUSE_RECT = Rect2i(35, 0, 3, 3)`,
* 2 只鸡(`CHICKEN_COUNT`),游荡范围 = 围栏内部的矩形。

**为什么**:随机撒点(multi-sample)会把围栏撒成一根根断头的柱子,看起来像 bug。
地标占了哪些格,在撒点前就写进 `reserved` —— 于是圈里**不会长树**,自检有一条
`nothing grows inside the pen` 钉着。

**围栏素材是个「十字路口」写法**:`Tilesets/Fences.png` 是 4x4 个 16x16,
每格 = 一根柱子 + 往左右的横杆(col 0 只有柱子 / 1 右横杆 / 2 左右横杆 / 3 左横杆),
横杆在 row 1/2。所以**只能拼横排**(左端 col 1、中段 col 2、右端 col 3),
竖排只有柱子可用 —— 图里根本没有竖向横杆,别凭空造。

**鸡**:`scripts/world/chicken.gd` 在代码里现造 `SpriteFrames`
(`Free Chicken Sprites.png`:row 0 = 2 帧 idle,row 1 = 2 帧 walk),
随机游荡 + `flip_h` 转身。它**故意没有 `class_name`**、用 `preload` 加载 ——
新增 `class_name` 要 `launch_editor` 重扫一次(见 `#class-name-cache`),这里不值得。

**验证**:围栏 18 段(2 排 x 7 + 4 根柱)全部站在**草地格**上(不是 props 格 ——
两套格坐标差半格,漂了的话围栏会整排站到水里,而水上看起来也「挺正常」);
每段都进了 `solid_cells`;2 只鸡都在围栏内部矩形里、都在播 2 帧动画。
截图复核:围栏矩形内检出 2 团鸡身奶油色像素 `(243,242,192)`(围栏/鸡舍的调色板里没有这个色)。

## <a id="prop-gather"></a>敲掉一个道具要**同时**腾三种状态

**决策**:`FarmProps.remove_at(cell)` 干三件事,缺一不可:
1. 它占的**每一个**格都从 `blocked`(别人不许再摆)和 `solid_cells`(玩家走不过去)里删掉;
2. 从 `placed` 里按**节点身份**摘掉那条记录;
3. 把节点从父节点上 `remove_child()` **再** `queue_free()`。

**为什么第 3 步要分两下**:`queue_free()` 要到帧末才真的把节点从 `children` 里去掉,
中间这段时间 `_collision_count()` 之类的遍历会看到「已经不该算进去的物件」——
砍完树碰撞形状数不变,自检就会莫名其妙地报差一两个。

**返回值约定**:`use_tool()` 返回 `{message, item, amount}`,`item == ""` 表示**什么都没发生**
(拿斧头砍石头),调用方**不要**动背包;`player.gd` 只负责把 `item/amount` 丢给
`GameState.add_item()`,规则本身不在玩家脚本里。

**自检**(`-- axe / pickaxe`,13 条):镐子砍树什么也不给且给出「只能敲石头」的提示、
斧头砍树 +2 木、树**整棵**消失(不是只掉一格)、`solid_cells`/`blocked` 都腾干净、
可站立格数正好多出 `size.x * size.y`、空地敲一下什么都不给、斧头不吃石头、镐子敲石头 +1 石、
以及**走玩家那条真实链路**(选工具 → 面朝树 → `use_current_tool()` → 木头进背包 → HUD 上的数字跟着变)。

## <a id="test-placement-frames"></a>测试里摆玩家:格坐标必须**从游戏自己的换算走**

踩了两次,都是同一类错——**两套格坐标的偏移不是整格**:

1. 想验「面朝一棵树按斧头」,就把玩家 `global_position` 放到
   `props.cell_center(树下面那格)`。结果目标格变成了树**下面**那格 —— 因为
   目标格是用**脚下的碰撞圆**(身体中心 + 6px)算的,身体中心和脚下差 6px,
   而 props 格和农田格在 y 上差半格多,一叠加就整差一格。
   正确写法:先问出「农田 (0,0) 对应 props 哪一格」
   (`walkers.props_cell_of(Vector2i.ZERO)`),再 `farm_plot.cell_center(对面那格)` 摆人 ——
   偏移是从游戏代码里**问**出来的,不是写死的 (20,7)。(相关的坑见 `#frame-mixing`。)
2. 断言「斧头动画 == 锄头动画」时,拿两个 `AtlasTexture` 用 `==` 比 —— 它们指向
   同一块图集区域,但**是各自 new 出来的对象**,永远不相等,报了个假 FAIL。
   比贴图内容要用 `_same_image()`(逐像素比 `Image.get_data()`)。

## <a id="prop-art-rects"></a>道具 rect 必须**一条 = 一个精灵**:连通域会把挨着的邻居圈进来

用户报的是「**有些树好像倒下了,素材放的不对,树应该可以被砍**」。查下来是
同一个根:图集里**有些精灵是紧挨着摆的**,而 `PROPS` 的 rect 是拿连通域
(flood fill)从 alpha 蒙版上量出来的 —— 一涨水就把两块连成一块,rect 里
于是塞进了一个「不属于它」的邻居。

### 具体错在哪(四条,全是同一根)

1. `tree_autumn` = `Rect2(129, 34, 14, 28)`,kind `tree` + solid。
   那块地方其实是**一株麦子**:顶上一颗金黄色麦穗 `(130,34,12,12)`,底下
   接着 17px 高的细叶 `(129,46,14,17)`,两块被糊成一条 28px 高的矩形。
   三棵真树之外,这是唯一一个「树」变体 —— 随机撒出去 79 棵里有一部分是它,
   画面上就是**一坨倒在地上的东西**,而且挡路(玩家会撞上去)。
2. `bush_low` 和 `bush_wide_alt` 的右边各自**粘了一截树桩**
   (`(25,71,7,7)` / `(60,68,8,9)`,100% 木色)。灌木是 deco(不挡路、不可砍),
   于是画面上是「一丛草旁边横着一截木头」——**这就是用户说的「树好像倒下了」**,
   拿斧头敲它还什么都没反应。
3. 三朵**大粉花**被标成了石头:`rock_mossy` `(82,2)`、`rock_pile` `(33,33)`、
   `rock_wide` `(64,49)` —— 全是粉瓣 + 白心 + 绿茎,却被标成 `kind: rock` + solid:
   玩家会撞在一朵花上,拿镐头敲花还能出石头。反过来,图集里**真正的**四块灰石
   (`(128,18)` `(80,67)` `(99,68)` `(114,18)`)当时被标成了 deco 灌木。
4. 22 条 rect 一律**少了最下面一行**(`h = max_y - min_y`,少加了 1)。
   树、灌木的脚下阴影被切掉一条;`bush_low` 这种矮物件直接少一行实体像素。

### 怎么修

- 重新量:先**腐蚀** alpha 蒙版(只留四邻全实的像素)当种子,再在原始蒙版上
  做**多源 BFS** 把每个像素判给最近的种子 —— 勉强能把粘着的两块分开;
  分不开的(灌木 + 树桩就是分不开,接触面有一像素厚)靠**颜色家族**手工切开。
- 颜色家族(不是形状)重判 kind:绿=草/灌木/花叶,灰白=石,木色=木头/树桩,
  粉/黄+绿=花。粉色的**只能**是 deco。
- 两截树桩正式登记成 `stump_log` / `stump_tiny`(kind `wood`,斧头能砍 → 1 木材);
  麦子变成 `wheat_plant`(deco,不挡路);石头 6 种;花 14 种;树 3 种(其中
  `tree_big_mirror` 改名 `tree_flower`:轮廓和 `tree_big` 一样,但树冠上点了粉花,
  是「开花的树」,**不是**镜像贴图)。
- 现在 `PROPS` 共 47 条:tree 3 / rock 6 / wood 7 / deco 26 / fence 4 / house 1。

### 规矩(以后照做)

- **一条 rect = 一个精灵**。判据很便宜:把 rect 里的像素按颜色家族分类,取
  「主色家族 ∪ 半透明阴影」的包围盒,它应当**正好**等于这条 rect(±1px)。
  比 rect 小 = 圈进了邻居。
- 改完表必须跑两样东西:
  - `python tools/check_props.py` —— 干净 / 分类 / 重不漏(退出码 0 = 全过);
  - `python tools/annotate_props.py` → **`docs/art/props_sheet.png`**:图集放大 6 倍,
    每条 rect 描边 + 编号,下面按编号列出名字/kind/rect/占地几格。
    **拿不定「这格素材是什么」的时候就靠这张图问人**(助手看不到图)。
- 引擎侧也加了回归断言(见下),因为这类错**不会报任何错**,逻辑测试全绿照样画错。

### 测试

- `_test_prop_art()`(引擎侧,调色板和离线工具同一张表):
  每条 rect 在图集内、没有邻居粘进来(47/47)、没有两条共用 rect、
  kind 和调色板对得上(`rock` 必须灰(粉 ≤5%)、`wood` 必须木色(绿 ≤20%)、
  `tree` 必须有绿树冠 + 木树干)、贴图不大于占地格数、deco 一律不 solid。
- `_test_every_wood_variant_is_choppable()`:按**变体名**遍历,把世界里出现的
  **每一种**树和木头都真的砍一遍 —— 10/10 变体全部能砍、全部给木材。
  (只测 `first_solid_cell("tree")` 会漏掉「某个变体的 kind 写错了」。)
- 自检从 223 → **231 checks, 0 failed**。

## <a id="dog-pet"></a>宠物狗:外部素材要过 `tools/pack_*.py`,跟随靠「重走脚印」

用户给了一张自己的狗素材(`C:\Users\E\Downloads\lilpuddinpuggums.png`),要求加进游戏。
它**不是** Sprout Lands 包里的东西,所以走了一套「外部素材接入」的流程。

### 素材:96x192 的白底图,3 列 x 4 行

- 原图是 **RGB、白底**(没有 alpha)。白色 12668 px,而且**全部和画布边缘连通**
  (没有一处被图形围住的白色)→ 可以放心把白色抠成透明;包围在里面的白不能抠。
- 版式:**3 列 x 4 行,每格 32x48**;狗本身只有 26~28 x 22~24,**画在每格底部**,
  上面是空的。第 0 行 = 正面(有粉舌头 `(235,47,181)`,验正面就看它),
  第 1 行 = 朝左,第 2 行 = 第 1 行的**逐像素镜像**(验过 `(1,c) == mirror((2,c))`),
  第 3 行 = 背面(没有粉/黄/灰)。第 0/1/2 列的竖直偏移不同,那是作者画的走路颠动,
  **保留**(不是脏数据)。
- 原图是**整数倍(2 倍)放大**过的:18432 个像素里只有 152 对不相等,且都在舌头/脚上
  → 缩小要用 **2:1 取样**,不要插值。
- **镜像轴落在半个源像素上**:直接按 `x*2` 取样,朝左/朝右两行的相位会差一格,
  左右帧就不是精确镜像了(转身会闪一下)。修法:朝右那一行从**奇数 x** 开始取样
  (`PHASE_X = {"right": 1}`)。改完验过:**左右帧 0 个像素不同**。
- 尺寸:农夫是 48x48 格里 14x16,鸡是 16x16 格里 11x12;源图的狗 26x24 太大,
  **0.5 倍**后 11~12 px 高,和鸡一个量级。
- 抠底 + 按行居中都在**缩小后的小图**上做 —— 源图的横向偏移是奇数,在大图上居中
  会差半个像素。
- `tools/pack_dog.py` 产出 `game_source/Pets/pug_walk.png`(48x96 = 3 列 x 4 行 16x24)
  和人工核对图 `docs/art/pug_sheet.png`(原图带格线 + 成品放大 8 倍 + 调色板)。
  原图原样留在 `game_source/Pets/lilpuddinpuggums.png`(管线输入,**不改**)。

### 跟随:重走脚印,不直线追

- 狗是 `CharacterBody2D`,精灵在代码里搭(`chicken.gd` 的路子,免得图集坐标在
  `.tscn` 和 `.gd` 里各写一份)。
- 精灵 `offset = Vector2(0, -CELL.y/2)`:**原点落在狗脚下**,于是 `position` 可以
  直接当地面落点用。符号写反了整只狗会挂到地底下 —— 和 `#cell-sprites` 一样是
  **不报错**的错法,所以自检里量了「最低一行不透明像素离原点多远」(实测 -1.0)。
- 追法:**每走 6px 记一个玩家的脚印**,狗沿脚印走。直线追会在树/水上顶死
  (道具是散在草地上的,直线必然穿树),而重走脚印**天然绕开**所有障碍。
- 已经跟上了(剩余脚印长度 ≤ 20px)就清空脚印、**面朝玩家**停下 —— 不清空的话
  玩家绕一圈回到原地,狗会照着圆圈再跑一遍。
- 卡住 0.35s 就丢掉当前脚印点(玩家贴着障碍另一侧走时会发生)。
- 图层:`collision_layer = 2`、`collision_mask = 1` —— 狗**不挡玩家**(玩家的 mask
  是 1,碰不到层 2),它自己也撞不进水/树。自检断言了这条**双向**不挡。
- 撒道具时 `farm_props.keep_clear` 为每只动物保留 3x3 格,免得树长在狗身上。

### 测试

- 自检里造一堵临时的墙(`_make_test_wall`,层 1),让玩家绕过它走,断言**狗的 y 曾经
  高过墙顶** —— 直线追的实现会顶死在墙上、这一条必挂。
- 位置不写死随机地形:整段跟随测试都在出生点周围被保留下来的空地里跑。
- 停下来要**面朝玩家**(不是面朝上一段路):断言用的是「实际相对位置的主轴」,
  第一版写死 `'right'` 反而报错 —— 狗绕完墙停在玩家上方,面朝下才对。

## <a id="selftest-await"></a>自检里带 `await` 的测试函数必须 `await` 调用

`_test_ponds()` 内部有 60 个物理帧的推墙循环(`await get_tree().physics_frame`),
它一开始是**不 await 直接调**的。GDScript 里这样的调用会返回一个协程对象、立刻往下
执行,于是:

- 池塘测试「推 60 帧再量落点」和它**后面**的测试交替执行;
- 后面那个测试(宠物狗)也会摆玩家位置、也要等物理帧;
- 池塘测试推完醒来,读到的是**狗测试摆的玩家位置** → 落点算出 416.8、期望 -221,
  报一个「塘墙不齐」的假失败。

判据:看到「和位置有关的断言莫名其妙地报错」,先看它所在函数**有没有 `await`**,
再看调用点**有没有 await 它**。加上 `await` 之后池塘测试恢复成精确的 -221.0(差 0.0)。

## <a id="cow-art"></a>`Free Cow Sprites.png` 是 3x2 的格子,但两行帧数不一样

`game_source/Characters/Free Cow Sprites.png`(96x64)按 32x32 切是 3 列 x 2 行,
看上去像「两个动作各 3 帧」的规则网格 —— **不是**:第 2 行第 3 格整格透明,
走路只有 2 帧。按 3 帧播会在走路时每隔一会儿闪一下空白,而且**不报错**、逻辑测试全绿。
切图集之前先逐格数 alpha。

哪一行是哪个动作也是量出来的(帧间差 + 差在哪些像素):

| 行 | 帧数 | 帧间差 | 差在哪 | 判定 |
|---|---|---|---|---|
| 0 | 3 | 4 / 12 px | 只有眼睛(x19..25, y17..18)和尾巴尖(x3..4) | **眨眼 / 站立** |
| 1 | 2 | 135 px | 犄角、头、腿、蹄子全在动 | **走路** |

- 牛只有**侧身**一套(没有正/背面):头朝右(眼睛和犄角在右边、尾巴在左边),
  往左走 `flip_h`。别去猜「哪一行是 front」。
- 贴图内容 27x17、最下面一行不透明像素(软阴影底边)在格的第 29 行。32 格居中 ⇒
  它默认画在 `position` 下方 13px,所以 `offset = (0, -(29-16)) = (0, -13)`,
  **原点落在牛脚上**。和狗一样,符号写反整头牛会浮空/钻地且不报错,
  自检里直接量「最低一行不透明像素离原点多远」。

## <a id="pasture"></a>牧场:地标手摆 + 活动范围往内收「半头动物」

围栏地标是**手摆**的(`PASTURE_RECT = Rect2i(33,10,7,9)`,贴在鸡圈下面、农田右边),
两处围栏共用 `_place_fence(rect)`:上下各一条横排 + 右边一列柱子,**左边留口**。
留口有两个原因:玩家能走进去;圈里不会变成走不到的**死角**(自检那条
「可行走格 90% 连通」会被死角拖下去)。

动物都是**不走物理的 `Node2D`**(`chicken.gd` / `cow.gd`):围栏已经挡住玩家了,
动物再当实体就会把玩家顶开。它们的活动范围由 `farm_props.gd` 注入:

- 鸡:圈内矩形(`_interior_rect(PEN_RECT)`)直接用 —— 鸡 11x12,贴不到围栏。
- 牛:`_interior_rect(PASTURE_RECT).grow(-COW_ROAM_INSET)`,往里再收 **18px**。
  牛 27x17,不这么做它的头(在活动范围上方 17px)会画到围栏上 ——
  又是「不报错、只在画面上看得出来」的一类。收多少 = 贴图内容尺寸的一半,
  换素材/换比例时要跟着改。

牧场占的 7x9 格在撒道具**之前**就写进 `reserved`(`for landmark in [PEN_RECT, HOUSE_RECT, PASTURE_RECT]`),
所以圈里不长树(自检:pen/house/pasture 里都不许有别的道具)。围栏 18 → 39 段,
树/石头/花草相应少了几个 —— 这是**预期**的,不是回归。
